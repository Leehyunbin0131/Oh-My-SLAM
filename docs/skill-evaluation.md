# ROS 2 스킬 평가 기록 규격

[README](../README.md) · [통합 설계](architecture.md) · [구현 계획](roadmap.md) · [검증 기준](acceptance.md) · [기술 기준](baseline.md)

## 목적과 저장 위치

설치된 ROS 2 스킬이 실제 개발 판단과 검증 과정에 어떤 영향을 주었는지 객관적으로 남기기 위한 기록 규칙입니다. 프로젝트 작업 일지가 아니라 평가 데이터를 쌓는 규격을 정의합니다.

원본 이벤트는 설치 스킬의 `references/usage-recording.md`가 지정한 **저장소 바깥 평가 루트**의 `usage.jsonl`에 한 줄씩 추가합니다. 프로젝트별 집계와 근거 목록은 이 저장소 옆의 `Oh_My_SLAM_skill_evaluation`에서 관리합니다. 실제 로그와 개인 평가 자료는 공개 저장소에 커밋하지 않습니다.

## 적용 조건

| 스킬 | 적용 대상 |
| --- | --- |
| `ros2-development` | ROS 연결 설계, 패키지·노드·interface·launch·설정 구현, 빌드와 검증 |
| `ros2-troubleshooting` | 실행 상태를 직접 봐야 알 수 있는 QoS, TF, IMU, odometry 문제 진단 |

스킬 문서를 열어 읽기만 하고 현재 작업에 쓰지 않았다면 `review_only`로 남기고 실제 적용 횟수에는 넣지 않습니다. 참고 파일을 여러 번 읽거나 하나의 적용이 여러 턴에 걸쳐 이어지더라도 사용 횟수를 중복해서 올리지 않습니다.

## 이벤트 모델

| 필드 | 의미 |
| --- | --- |
| `usage_id` | 논리적인 스킬 적용 1건의 식별자(같은 적용의 start/observation/finish가 공유) |
| `event` | `start`, `observation`, `finish` |
| `recorded_at` | 실제 기록 시각과 시간대 |
| `skill`, `installed_file_sha256` | 적용한 스킬 이름과 설치본 파일 해시 |
| `workspace`, `application` | 대상 프로젝트와 적용 방식 |
| `instruction` | 실제 판단에 참고한 지침 |
| `action` | 지침대로 처리했거나 다르게 결정한 내용 |
| `result`, `artifacts` | 실제 결과와 확인 가능한 근거 파일 경로 |
| `helpfulness` | `helpful`, `partial`, `not_helpful`, `unclear`와 판정 이유 |
| `benefit_assessment` | 관측 결과, 기존 지식·사용자 규칙과의 중복 여부, 인과 효과 확인 수준 |
| `costs` | 실제로 늘어난 도구 호출, 실패, 재작업(측정하지 않은 시간·토큰·비용은 null) |

계획 단계 내용은 `declared_plan`, 실제 관찰한 사실은 `observed`, 도움 여부에 대한 해석은 `assessment`로 나눕니다. 돌리지 않은 테스트나 확인하지 않은 실물 효과를 `finish` 결과에 적지 않습니다.

## 집계 기준

- **실제 사용 횟수:** 프로젝트에 속한 고유 `(usage_id, skill)` 가운데 실제 적용 이벤트가 있는 건수입니다.
- **완료 수:** 위 적용 중 `finish` 이벤트까지 기록된 건수입니다. 진행 중 건수는 실제 사용 횟수에서 완료 수를 빼서 구합니다.
- **열람 건수:** 실제 적용 없이 읽고 끝난 `review_only` 논리 건수입니다. 파일을 몇 번 열었는지로 세지 않습니다.
- **도움 판정:** 완료된 적용의 최종 판정을 집계합니다. 판정이 비어 있으면 `unclear`로 둡니다.
- **도움 비율:** 사례가 충분히 쌓인 뒤 `helpful`, `partial`, `not_helpful`, `unclear`를 각각 따로 공개합니다. `partial`을 성공에 합쳐서 하나의 성능 개선율처럼 부풀리지 않습니다.

중복 이벤트가 들어와도 사용 횟수를 늘리지 않습니다. 정정할 내용이 생기면 기존 행을 고치지 않고 정정 이벤트를 새로 추가해 최신 판정을 씁니다.

## 도움 판정과 성능 주장의 경계

| 판정 | 필요한 근거 |
| --- | --- |
| `helpful` | 특정 지침이 판단이나 검증 방법을 실제로 바꿨고 그 결과가 근거로 확인됨 |
| `partial` | 구조화나 누락 방지에는 일부 도움이 됐지만 기존 규칙과 겹치거나 독립 효과가 분리되지 않음 |
| `not_helpful` | 판단 변화가 없었거나 적용 때문에 불필요한 비용만 늘어난 것이 확인됨 |
| `unclear` | 판단이나 실행 근거가 부족해 도움 여부를 가리기 어려움 |

테스트가 통과했다는 사실은 작업 결과일 뿐 스킬 덕분에 성능이 올랐다는 증거가 아닙니다. 코드를 직접 읽어 찾은 내용이나 공식 문서, 하위 에이전트 검토에서 나온 결과를 스킬 효과로 바꿔 적지 않습니다. 인과적인 성능 개선을 말하려면 같은 작업, 모델, 도구, 검증 조건을 맞춘 별도 비교 기준선이 있어야 합니다.

스킬 기록을 채우려고 새 로봇 시험이나 긴 비교 실험을 억지로 만들지 않고, 실제 프로젝트 작업에서 자연스럽게 나온 근거만 씁니다.
