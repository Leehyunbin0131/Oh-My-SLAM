# 인수 검증 기준과 기록 방법

[README](../README.md) · [통합 설계](architecture.md) · [구현 계획](roadmap.md) · [기술 기준](baseline.md)

각 단계(`P1`–`P8`)를 완료로 보려면 통과해야 하는 통합 검증 시나리오 `V1`–`V8`, 통과 수치 기준, 실패 주입 항목과 기록 구조를 정리했습니다. 하드웨어와 제어 계층 규격은 [기술 기준과 호환성](baseline.md)을 참고하면 됩니다.

## 단계별 최소 검증

| 검증 | 대상 | 한 번의 묶음에 포함할 항목 | 통과 기준 |
| --- | --- | --- | --- |
| V1 | ROS base·mock | 기구학, 부호, 명령 수명, 큐 지연, fault, 원시 엔코더 적분, 설치본 | 정해진 입력 계산값 일치, 재송신으로 원본 age 증가 없음, stale 명령 재활성화 0회 |
| V2 | Sim base·센서 | 짧은 전진·회전, TF, 시각, 타입, pause/resume | 전진 +X·좌회전 +yaw, TF 각 edge 단독 발행, `/clock` 혼용 없음, resume 후 새 명령 요구 |
| V3 | Sim mapping/localization | 폐루프, map·graph 저장, AMCL 재시작 | 중복 벽이나 지속적 TF 오류 없음, 저장 파일 재로딩 성공, truth 대비 위치 ≤0.15 m·yaw ≤0.20 rad |
| V4 | Sim State Lattice+DWB | 한 실행에서 목표 5곳 연속 도착, 같은 기록의 센서·TF·인지·명령·충돌 관측 | 5/5 action 성공과 측정 정지, 위치 ≤0.15 m·yaw ≤0.20 rad, 측면 명령 0, 충돌 0회, 구동 한도 준수 |
| V5 | Real base·odom/IMU | 새 ROS 경로 구동, 1 m 직진, 양방향 회전, 짧은 폐루프, 저속·정지 | 직진 거리 오차 ≤5%, 360° 회전 오차 ≤5%, 부호·축 정상, 원본 명령 timeout과 fault 처리 확인 |
| V6 | Real SLAM/AMCL | 실제 폐루프, 저장, 두 위치 재초기화 | 기준 표식 대비 위치 ≤0.15 m·yaw ≤5°, 벽 이중화나 지속적 scan drop 없음 |
| V7 | Real 저장 지도 Nav2 | 목표 3개, 취소·재출발, 장애물, 센서 중단 | 위치 ≤0.15 m·yaw ≤0.20 rad, 접촉 0회, 실제 여유가 footprint+padding 충족 |
| V8 | Real online SLAM+Nav2 | 지도 확장, loop closure, 목표, 저장·재시작 | V7 목표 기준 유지, odom 연속, map 보정 후 경로·메모리 정합, 모드 전환 중 비의도 구동 0회 |

V5에서 양방향 회전을 따로 보는 이유는 좌우 방향에 따라 유효 윤거와 미끄러짐이 달라질 수 있기 때문입니다. 그렇다고 모든 속도와 센서를 무작정 조합해 시험을 늘리지는 않습니다. 저속 구간도 Nav2가 실제로 쓰는 속도와 현장에서 확인된 문제를 기준으로 골라 확인합니다.

V1의 수학 단위 시험은 부동소수점 허용오차를 코드에 직접 적어 둡니다. V3–V8의 위치와 각도 기준은 결과를 보고 나서 슬쩍 낮추지 않으며, 바꿀 이유가 생기면 이유와 적용 범위를 계획 문서에 남깁니다.

## 시간과 정지 판정

명령 처리가 끝난 시점과 로봇이 실제로 멈춘 시점은 따로 떼어서 기록합니다.

| 측정 항목 | 기준과 해석 |
| --- | --- |
| 원본 입력 deadline | 기본 300 ms. 원본 stamp, 수신 monotonic 시각, MCU lease를 함께 기록 |
| 모의 worker 출력 해제 | deadline 이후 1 worker 주기(20 ms) 안에 `STOP` 요청; OS 스케줄링 지연은 별도 |
| 실제 MCU 출력 해제 | 300 ms 명령 만료 기준으로 UART·MCU tick·측정 시각 오차 기록. 초기 목표 350 ms 이내, 실제 관측으로 판정 |
| 실제 정지 완료 | 최신 측정 속도와 상태, 눈으로 본 관찰을 같이 확인. ACK만 받고 정지했다고 보지 않음 |
| 제동 거리 | 시험 속도별로 따로 측정. 충돌 감시 거리에는 반응 지연 이동거리, 제동거리, padding 포함 |
| feedback freshness | 기존 400 ms 제한 유지. 브리지가 오래된 피드백에 새 stamp를 붙여 재발행하지 않음 |
| 정상 제어 주기 | 50 Hz 목표 송신, 실제 telemetry 약 20 Hz. p50·p95·p99와 긴 공백 기록 |
| planner/controller 부하 | 필요한 경로가 제때 갱신되는지와 command age를 함께 확인. CPU 점유율만으로 통과 판정하지 않음 |

이 수치는 개발용 기준일 뿐 안전 인증이나 기능 보장을 뜻하지 않습니다. 펌웨어 워치독이 출력을 푼 시각과 차체가 실제로 멈춘 시각을 섞어 쓰지 않으며, 시뮬레이션 정지 결과로 실물 차단 시간을 대신하지 않습니다.

## 실패 주입으로 확인할 항목

V1 모의 환경에서 한 번 확인해 두어야 할 항목은 다음과 같습니다.

- 원본 publisher가 끊겼는데 smoother가 같은 명령을 계속 내보내는 경우
- 원본 시각은 그대로인 채 평활 출력이 여러 번 들어오거나, 큐에서 지연된 명령, 오래된 메시지가 늦게 도착한 경우
- 0 명령이 지나간 뒤 늦게 들어온 nonzero 명령이나, 모드 전환 전에 남아 있던 저장 명령
- 원본 age가 200 ms를 넘긴 뒤 들어온 긴급·차단용 0 명령을 최소 lease 조건 때문에 건너뛰지 않고 바로 `STOP`으로 처리하는지
- 피드백 단절, CRC·프레임 오류, MCU fault, MCU clock 재시작과 정상 wrap
- deactivate나 재접속 직후 새 명령 없이 로봇이 다시 움직이지 않는지

실물 로봇에서는 이 모의 조합을 전부 다시 돌리지 않습니다. 실제 하드웨어 연결이 필요한 입력 중단, 브리지 중단, 피드백·센서 중단만 준비된 V5와 V7 세션에서 확인합니다.

## TF·시각·센서 확인 기준

- `map → odom`과 `odom → base_footprint`를 누가 발행하는지 기록하고 각각 하나뿐인지 확인합니다.
- 센서 transform은 실제 로봇에 달린 방향과 대조합니다. URDF 숫자가 서로 맞는다고 해서 실물 축이 맞다고 보지 않습니다.
- IMU의 중력 방향과 좌회전 yaw rate는 base 좌표계로 바꾼 뒤 확인합니다.
- wheel odom과 `/joint_states`는 실제 sample ID와 MCU tick이 새로 올라왔을 때만 갱신되어야 합니다.
- 시뮬레이션은 관련 노드 전부가 sim time을, 실물은 시스템 시각을 써야 합니다. 실물에서는 노트북과 Orin 사이 시각 동기화도 같이 확인합니다.
- 카메라 depth scale, intrinsics, optical frame, TF 시각, 장애물 기억 좌표계를 점검합니다. 깊이 값이 비어 있는 영역을 관측된 빈 공간으로 착각하지 않는지도 봅니다.
- 실물 지도와 시뮬레이션 지도는 메타데이터의 backend로 구분하고, 다른 backend 지도를 실물 launch 기본값으로 쓰지 않습니다.

## 빌드와 실행 근거

코드를 고친 뒤에는 `colcon list`로 패키지 의존 관계를 확인하고 `colcon build --packages-up-to <대상>`으로 빌드합니다. 빌드가 끝나면 새 셸에서 underlay와 이번 install을 source한 뒤 `ros2 pkg prefix <대상>`이 올바른 경로를 가리키는지 확인합니다.

테스트는 새 결과 디렉터리에서 돌리고, **건너뛰지 않고 실제로 실행된 검사 ID와 개수**를 남깁니다. `colcon test-result` 종료 코드가 0이거나 테스트가 비어 있다는 이유만으로 통과 처리하지 않습니다. launch나 설치 경로만 바뀐 경우에는 관련된 실행 확인만 수행하고 기존 동작 검사를 처음부터 다시 돌리지 않습니다.

아직 패키지가 없는 계획 단계에서 가짜 테스트나 빈 colcon 성공 기록을 만들지 않습니다.

## 기록 구조

검증 도구는 실행할 때마다 아래 구조로 결과 디렉터리를 만듭니다.

```text
reports/<stage>/<run-id>/
  manifest.json       # commit, 의존성 commit, config/calibration hash, backend, 장비/버전
  commands.json       # 실제 실행 명령, cwd, 종료 코드, 대상 package prefix
  results.json        # 검사 ID, 측정값, 기준, pass/fail/inconclusive
  summary.md          # 이번 범위의 결과와 실제 한계
  rosbag/             # 필요한 토픽만; 무거운 RGB 원본은 목적이 있을 때만
  logs/
```

입력 명령, wheel odom, filtered odom, IMU, TF, 진단, scan 토픽은 확인 목적에 맞게 골라 녹화합니다. 제어 주기가 밀릴 정도로 무거운 영상 토픽까지 무조건 전부 기록하지 않습니다.

공개 저장소에는 실내 지도, 원본 rosbag, 장비 주소나 인증정보를 올리지 않습니다. 공개가 필요하면 범위를 정한 요약과 그림만 따로 정리해 올립니다.

## 중단과 복구

- **빌드 실패:** 그 빌드 결과에 의존하는 실행 검증은 바로 멈춥니다. 이전 install을 그대로 써서 대신 검증하지 않습니다.
- **방향·TF 오류, 예기치 않은 재출발, 정지 불응:** 해당 실물 시험을 즉시 중단하고 원인을 고친 뒤 영향받는 검사만 다시 합니다.
- **지도 정합 실패:** Nav2를 올려서 문제를 덮지 않고 odom과 센서 frame, 시각부터 원인을 잡습니다.
- **롤백:** 소스 commit, calibration hash, map metadata를 세트로 맞춥니다. 기존 `ros2_dev_ws`나 `robot_mapping_ws`를 새 workspace와 동시에 띄우지 않습니다.

합의한 구현과 해당 단계의 필수 검증이 통과하면 그 단계는 완료입니다. 다음 단계 항목이나 이번 범위 밖 기능을 현재 단계의 미완성으로 남겨 두지 않습니다.
